# ESP32-C3 native node firmware

## Purpose

`firmware/c3-node` is the Phase 3.5 connectivity bootstrap for an ESP32-C3 SuperMini. It validates:

```text
ESP32-C3 -> Wi-Fi -> MQTT -> local EMQX
```

It uses the persisted EdgeOps Device UUID as its MQTT client identity and topic identity. It does not publish Device Channel values and has no Go subscriber, command handling, semantic model, or provisioning flow.

## Tooling

The project targets ESP-IDF 5.3 or newer and the `esp32c3` target. The detected development installation is ESP-IDF 6.1 with the RISC-V GCC 15.2.0 toolchain. Since ESP-IDF 6 moved ESP-MQTT to the Component Manager, `main/idf_component.yml` pins the compatible `espressif/mqtt` 1.1 release line. The same managed component supports ESP-IDF 5.3+.

After installing ESP-IDF, activate its environment in every new shell:

```bash
source /path/to/esp-idf/export.sh
idf.py --version
```

## Structure

```text
firmware/c3-node/
  CMakeLists.txt
  sdkconfig.defaults
  main/
    Kconfig.projbuild
    app_main.c
    edgeops_device.[ch]
    edgeops_wifi.[ch]
    edgeops_mqtt.[ch]
```

- `edgeops_device` owns identity, version, topic construction, and small JSON payloads.
- `edgeops_wifi` owns station events and bounded reconnect backoff.
- `edgeops_mqtt` owns presence, Last Will, heartbeat, and MQTT reconnect state.
- `app_main` initializes NVS and starts connectivity.

## Configuration

Local configuration is generated by ESP-IDF and excluded from Git. No Wi-Fi or MQTT password is committed.

```bash
cd firmware/c3-node
idf.py set-target esp32c3
idf.py menuconfig
```

Open `EdgeOps C3 Node` and set:

- Wi-Fi SSID;
- Wi-Fi password;
- MQTT broker URI, for example `mqtt://192.168.1.20:1883`;
- persisted EdgeOps Device ID;
- optional device name;
- development heartbeat interval.

The seeded Phase 3 Device ID is:

```text
00000000-0000-4000-8000-000000003000
```

Use the actual ID shown by `GET /api/v1/devices/{deviceID}` if the development Device was recreated. The broker URI must use the development computer's LAN address reachable by the ESP32; `localhost` on the ESP32 is not the computer.

## Build, flash, and monitor

```bash
cd firmware/c3-node
idf.py set-target esp32c3
idf.py menuconfig
idf.py build
idf.py -p /dev/ttyACM0 flash
idf.py -p /dev/ttyACM0 monitor
```

The C3 SuperMini serial device may instead appear as `/dev/ttyUSB0`. Build, flash, and monitor can be combined:

```bash
idf.py -p /dev/ttyACM0 flash monitor
```

Exit the ESP-IDF monitor with `Ctrl+]`.

The firmware has been build-verified for the `esp32c3` target with ESP-IDF 6.1, RISC-V GCC 15.2.0, and `espressif/mqtt` 1.1.0. Physical flash and broker behavior still require hardware verification.

## MQTT topics

For Device ID `{deviceId}` the firmware uses:

```text
edgeops/v1/devices/{deviceId}/up/presence
edgeops/v1/devices/{deviceId}/up/state
```

The namespace also reserves, but this firmware does not use:

```text
edgeops/v1/devices/{deviceId}/up/events
edgeops/v1/devices/{deviceId}/up/telemetry
edgeops/v1/devices/{deviceId}/down/commands
edgeops/v1/devices/{deviceId}/down/config
```

### Presence and Last Will

On every MQTT connection the node publishes online presence with QoS 1 and retain enabled:

```json
{"status":"online","firmwareVersion":"0.1.0","hardware":"esp32-c3","deviceName":"Control Node #1"}
```

The same topic has a retained QoS 1 Last Will:

```json
{"status":"offline"}
```

Retain gives a newly connected observer the last known presence. QoS 1 is appropriate for low-volume state transitions. An unexpected power/network loss causes EMQX to replace retained online presence with the offline Will. A graceful MQTT disconnect does not publish a Will; graceful shutdown presence can be added when the firmware has an explicit shutdown lifecycle.

### State heartbeat

While connected, the node publishes every 10 seconds by default:

```json
{"firmwareVersion":"0.1.0","uptimeSeconds":120,"freeHeapBytes":123456}
```

State uses QoS 0 and is not retained because it is frequent, diagnostic, and immediately superseded. This interval and message are development diagnostics, not the production telemetry contract.

## Reconnect behavior

- Wi-Fi uses ESP-IDF events and a one-shot timer with backoff from 1 to 30 seconds.
- A successful IP acquisition resets Wi-Fi backoff.
- MQTT starts after the first IP address is acquired.
- ESP-IDF MQTT automatic reconnect is enabled with a five-second retry timeout.
- Every MQTT reconnection republishes retained online presence.
- Heartbeats pause while MQTT is disconnected and resume after reconnection.

## EMQX validation

Start or confirm local infrastructure:

```bash
docker compose -f infra/docker/compose.yaml up -d
docker compose -f infra/docker/compose.yaml ps
```

From a machine with Mosquitto clients installed, observe the complete native-device namespace:

```bash
mosquitto_sub \
  -h 127.0.0.1 \
  -p 1883 \
  -t 'edgeops/v1/devices/00000000-0000-4000-8000-000000003000/#' \
  -v
```

Then:

1. boot the ESP32 and confirm retained `online` presence;
2. confirm state messages arrive at the configured interval;
3. inspect the connection in EMQX Dashboard at `http://localhost:18083`;
4. remove device power or Wi-Fi without a graceful disconnect and confirm retained `offline` presence;
5. restore connectivity and confirm `online` replaces it and state resumes;
6. restart EMQX and confirm the device reconnects automatically.

The local dashboard development login comes from Compose (`admin` / `edgeops`). These credentials are not device credentials.

## Security and development limitations

Phase 3.5 permits unauthenticated plain MQTT only on the isolated local development broker. Production requires MQTT over TLS with unique per-device authentication, broker ACLs, credential rotation, and eventually certificate-based provisioning.

Known limitations:

- configuration is manual through `menuconfig`;
- Wi-Fi credentials reside in local flash/sdkconfig without production secure provisioning;
- no TLS, MQTT authentication, or per-device ACL is configured;
- no GPIO/channel telemetry, commands, offline buffer, OTA, or semantic runtime exists;
- the Go API and frontend do not consume presence yet;
- JSON strings assume the configured display name does not contain characters requiring JSON escaping.
